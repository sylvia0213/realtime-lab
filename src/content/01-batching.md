实时界面的第一个问题，经常不是如何画出曲线，而是数据持续到达时，应用到底做了多少工作。这篇文章记录本站实验室的实现，所有数据均由模拟器生成。

## 先拆开三种频率

收到消息的次数、通知订阅者的次数、React 最终提交的次数，并不是同一件事。React 可能批处理更新，因此不能把一次 `setState` 或一次 store 通知直接当成一次屏幕刷新。

实验室展示的是**接收条数**与**状态通知次数**。这些是代码实际计数；它不把通知合并比例称为 CPU 降幅，也不把它当成 FPS。

## 数据先处理，通知再合并

每一条消息都先经过格式校验，再按 topic 检查序号。只有新消息进入最新值和历史窗口。批量模式每 100ms 最多启动一次待执行通知，把此时最新的快照交给 React。

```ts
if (interval === 0) {
  flush();
} else if (!flushTimer) {
  flushTimer = setTimeout(() => {
    flushTimer = undefined;
    flush();
  }, interval);
}
```

这里减少的是通知频率，并没有省掉消息解析。高输入量下，JSON 解析、数据结构维护仍然会消耗主线程时间；更高负载可能需要 Worker、二进制协议或服务端聚合。

## 快照必须稳定

React 使用 `useSyncExternalStore` 订阅客户端。`getSnapshot()` 返回缓存的对象，只有发布更新时才创建新对象。否则即使数据没变，每次读取都返回新引用，也会破坏外部存储订阅的稳定性。

历史窗口最多保留 240 条记录。这个数量是实验的展示上限，不是消息不丢失的承诺。业务若需要完整明细，应另外设计持久化与回放机制。

## 自己动手验证

1. 打开实验室，选择每秒 100 条消息。
2. 先用“逐条通知”运行一段时间，记录接收条数和状态通知次数。
3. 切换到“100ms 批量”，统计会从切换点重新计算。
4. 提高到每秒 1,000 条，再观察两项计数的关系。
5. 若要比较实际渲染成本，在同一浏览器、同一负载和相同运行时长下录制 React Profiler / Chrome Performance。

浏览器后台会限制计时器，所以设定的发送速率不是吞吐量保证。应该记录实测接收量，而不是拿配置值当实测值。

## 什么数据不能这样处理

曲线的最新值通常适合合并展示，但订单完成、失败告警等状态转换可能必须及时呈现。先划清业务语义，再决定按时间窗口合并、按实体合并，还是立即通知。
