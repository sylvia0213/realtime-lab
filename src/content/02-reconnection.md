WebSocket 的 `open` 事件只说明传输通道建立了。它不证明断线期间的数据完整，也不证明旧订阅已经恢复。本站实验室将这几件事分开处理。

## 恢复连接，再恢复订阅

客户端保存的是当前需要的 topic 集合。每次新连接打开，重新发送完整订阅集合，而不是依赖旧连接留下的状态。停止客户端时，同时关闭连接和取消待执行的重试计时器。

重试采用有上限的指数退避，并加入随机扰动。它让多个客户端不至于始终在完全相同的时间重试。演示实现最多连续重试 5 次，收到有效的新数据后重置失败次数。

## 防止旧连接继续写入

关闭连接并不意味着所有异步回调都已消失。客户端为每一代连接分配一个编号；回调执行时检查它是否仍属于当前连接，并检查用户是否仍希望保持运行。

```ts
const generation = ++this.generation;
const active = () =>
  this.wanted && generation === this.generation;

socket.onmessage = event => {
  if (active()) this.receive(event.data);
};
```

这是对迟到回调的第二道检查。取消计时器、移除处理器以及代际检查各有职责。

## 去重不等于补偿

演示协议为每个 topic 提供单调递增的 `seq`。收到小于或等于最近序号的消息时忽略；收到跨越序号的消息时累加缺口数。

**发现缺口不代表已经补齐。** 这个项目没有实现服务端历史回放，也没有伪装成“断线零丢失”。真实业务可以在发现缺口后重新获取权威快照，再按服务端协议衔接增量事件。

序号语义必须先与服务端约定：是否跨重连连续？是否按 topic 隔离？重启后是否归零？如果这些前提不成立，不能直接套用本例的去重逻辑。

## 两种运行方式

默认模拟器在浏览器内产生合成数据，用来复现 UI 和连接生命周期；它不会建立真实网络 WebSocket。

源码另外提供本地 WebSocket 服务：运行 `npm run mock-server`，再在本地网站的实验室切换数据源。该服务持续生成三路数据，连接中断时服务仍继续生成，所以重连后可能看到序号缺口。公网预览默认使用浏览器模拟器。

## 测试重点

最需要验证的是：重连后是否重新订阅、停止后是否仍重试、迟到消息能否污染新状态、无效数据是否被拒绝、历史窗口是否始终有界。单纯断言连接对象被创建，不能覆盖这些用户可见的行为。
